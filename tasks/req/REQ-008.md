# Goal

将需求状态机中的 `owner` 字段从硬编码模型名（`claude`、`codex`、`daniel`）替换为角色 UID（`optimizer-001`、`evaluator-001`、`human-001`），并引入 `harness/agent-registry.yml` 作为唯一注册表。

这一变更体现了 Anthropic Harness 实践中 Optimizer/Evaluator 角色与具体模型实例的解耦：今天 optimizer-001 是 Claude claude-sonnet-4-6，未来可以替换为任何其他模型，而 REQ 文件和状态机逻辑不需要变更。

# Background

当前 `owner` 字段直接写模型名（`claude`/`codex`），绑定了角色与实现。如果：
- 引入第二个 optimizer（并行开发两个 REQ）→ 无法区分
- 切换到不同 LLM 提供商的 optimizer → 必须批量修改所有 REQ 文件
- 添加 evaluator 角色（如一个专门做 security review 的 evaluator-002）→ hardcoded 校验脚本无法扩展

UID 注册表解决这三个问题。

# In Scope

1. **`harness/agent-registry.yml`** — 角色注册表（source of truth）
   - 三条初始记录：`optimizer-001`（Claude）、`evaluator-001`（Codex）、`human-001`（Daniel）
   - 每条记录含：`uid`、`role`、`model`、`description`、`handles`（该角色有效工作的 REQ 状态列表）

2. **`.env.example`** — 新增 `AGENT_UID` 变量，预填 `optimizer-001`，注释说明各 agent 的取值

3. **`scripts/claim-req.sh`** — 重写校验逻辑
   - 接受 UID 格式：`bash scripts/claim-req.sh REQ-NNN` （从 `$AGENT_UID` 读取）
   - 或显式传入：`bash scripts/claim-req.sh REQ-NNN optimizer-001`
   - 从 `harness/agent-registry.yml` 动态读取该 UID 的 `handles` 列表，替代 hardcoded case 分支
   - 未知 UID → HARD STOP

4. **`harness/req-constants.sh`** — valid owners 改为从注册表动态派生（所有已注册 UID + `unassigned`），不再硬编码模型名

5. **`harness/requirement-standard.md`** — 更新 §3 frontmatter schema（`owner` 字段示例改为 UID 格式）和 §6 Agent Handoff Protocol（`claim: REQ-NNN by optimizer-001`）

6. **`harness/GLOSSARY.md §13`** — 更新 owner 枚举表，从模型名改为 UID 格式，说明注册表位置

7. **`CLAUDE.md`** — 新增"Agent Identity"节：说明本 Claude 实例注册为 `optimizer-001`，启动时读取 `.env` 的 `AGENT_UID`

8. **`AGENTS.md`** — 同步更新为 Codex 对应说明（`evaluator-001`）

9. **存量 REQ 迁移**（REQ-001 ~ REQ-007）
   - `owner: codex` → `owner: evaluator-001`
   - `owner: claude` → `owner: optimizer-001`
   - `owner: daniel` → `owner: human-001`
   - （`owner: unassigned` 不变）

# Out of Scope

- 运行时自动注册（agent 启动时写入注册表）— 静态注册表足够，不需要动态注册
- 多实例并行（optimizer-002）— 注册表格式已为此预留，但本 REQ 不创建第二个实例
- 自动化 inbox/handoff 系统 — 已在 CONNECTORS.md §2 推迟

# Acceptance Criteria

- AC1：`AGENT_UID=optimizer-001 bash scripts/claim-req.sh REQ-NNN` 在 REQ 处于 optimizer 有效状态时退出码 0
- AC2：`AGENT_UID=evaluator-001 bash scripts/claim-req.sh REQ-NNN` 在 REQ 处于 evaluator 有效状态时退出码 0
- AC3：`AGENT_UID=unknown-uid bash scripts/claim-req.sh REQ-NNN` 退出码 1，报错 "Unknown UID"
- AC4：`AGENT_UID=optimizer-001 bash scripts/claim-req.sh REQ-NNN`（REQ owner 为 `evaluator-001`）退出码 1，报错 owner 不匹配
- AC5：`bash scripts/check-req-coverage.sh` 在 REQ owner 为有效 UID 时通过
- AC6：`bash scripts/check-req-coverage.sh` 在 REQ owner 为旧格式（`claude`/`codex`/`daniel`）时报错
- AC7：`harness/agent-registry.yml` 存在且包含 `optimizer-001`、`evaluator-001`、`human-001` 三条记录，每条含 `uid`、`role`、`model`、`handles` 字段
- AC8：`.env.example` 包含 `AGENT_UID=optimizer-001` 及注释
- AC9：所有 REQ-001 ~ REQ-007 的 `owner` 字段均为 UID 格式

# Test Case Design Notes

由 Codex 在 `tc_design` 阶段设计 TC 文件（`tasks/test-cases/TC-008-*.md`）：

- **TC-008-01**：claim-req.sh 正常路径 — optimizer UID + REQ 处于 `req_impl` 状态 → 退出码 0
- **TC-008-02**：claim-req.sh 正常路径 — evaluator UID + REQ 处于 `req_impl_review` 状态 → 退出码 0
- **TC-008-03**：claim-req.sh 未知 UID → 退出码 1，stderr 含 "Unknown UID"
- **TC-008-04**：claim-req.sh owner 不匹配 → 退出码 1，stderr 含 owner 值
- **TC-008-05**：claim-req.sh 旧格式 UID（`claude`）→ 退出码 1（migration 完成后旧格式不在注册表）
- **TC-008-06**：check-req-coverage.sh 接受 UID 格式 owner → 通过
- **TC-008-07**：check-req-coverage.sh 拒绝旧格式 owner → 报错含 REQ ID 和字段名
- **TC-008-08**：registry 结构校验 — 所有必填字段存在，`handles` 列表非空

注意：TC 均为 L1（shell 脚本单元测试），可用 `bats`（Bash Automated Testing System）或等效手段实现。如项目未引入 bats，可用 pytest 的 subprocess 调用。

# Agent Notes

- **`harness/agent-registry.yml` 解析**：`claim-req.sh` 用 `awk`/`grep` 解析 YAML，不引入额外依赖。`handles` 字段为空格分隔的状态列表（行内格式）或 YAML sequence，选一种，脚本统一处理。
- **原子迁移**：`req-constants.sh` 更新和 REQ-001~007 文件迁移必须在同一 commit 中，否则会出现 `check-req-coverage.sh` 在迁移过渡期报错的窗口。
- **bootstrap 例外**：REQ-008 本身在 `req_review` 阶段使用旧格式 `owner: codex`（因为 UID 系统尚未实施）。实施完成后，REQ-008 自身也作为迁移的一部分更新为 UID 格式。
- **向后兼容**：实施完成后，旧格式（`claude`/`codex`/`daniel`）成为 **无效** owner 值，`check-req-coverage.sh` 报错。不保留过渡期宽容窗口。
